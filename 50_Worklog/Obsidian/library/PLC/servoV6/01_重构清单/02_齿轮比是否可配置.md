## 问题描述

> 现在面临的一个问题就是，按照汇川PLC自己的单位配置，可能丧失了部分灵活性：
>
> 实际配置齿轮比，有误差的时候，需要进入到 autoshop 中，然后按照以下流程进行配置
>
> ```bash
>  运动控制轴 - 换算单位计算“工作台旋转一圈的移动量” - 填写新的配置 - 烧录编译 PLC 程序
> ```
>
> 再进行验证。
> 但是好在这个场景，一般只发生在初始化电机的时候，就是第一次配置的时候的调试过程中。所以这个时间成本就还能接受。
>
> 另外一个想法就是，放开 PLC 的
>
> - 齿轮比
>
> - 齿轮外径
>
> - 丝杆螺距等参数配置
>   	
>
> 例如上位机发送了设置**单轴1**的速度为`10mm/s`命令后，此时有两个可选操作来决定如何转换为 PLC 的**单轴1**的速度。
>
> 1. 上位机读取保存在 PLC 的单轴1的齿轮比、外径的配置。
> 	然后通过计算，换算出最终映射到电机的脉冲数量。
> 	将速度转换为脉冲数后，将参数设置到PLC中。PLC 只接受脉冲为单位。
> 	
>2. 上位机直接将速度发送给 PLC ，PLC 内部通过转换，将其转换为电机的实际速度。（未经过验证）
>
> 但是这样的问题就是，我们需要抛弃掉已经定义好的齿轮比等单位换算的参数，需要重新加入一套这个换算逻辑，
> 这些逻辑涉及到了位置、速度所有的跟移动相关的配置。
>
> 现在问题就是，哪一个时间成本更高？现在工业成熟的体系中，更偏向于哪一个方案呢？

## 直接结论

工业成熟体系通常选择：

> 上位机、HMI、工艺程序全部使用工程单位（mm、mm/s、mm/s²、°）；脉冲/编码器计数与工程单位的换算，由 PLC 的运动轴对象或驱动器完成。

因此，在你提出的两个方案中：

- 方案 1“上位机计算脉冲并把脉冲发给 PLC”总体成本更高、风险更大，不建议作为 servoV6 的正式架构。
- 方案 2“上位机发送 mm、mm/s，PLC 运动轴完成换算”更接近 PLCopen、Siemens、Beckhoff、CODESYS 等成熟运动控制体系。
- 但不要在 PLC 的 ST 程序中再手写一套换算公式；应优先使用 AutoShop 运动轴原有的单位换算能力。
- 对当前项目，最合理的是先保留 AutoShop 编译配置，把齿轮比校准当作设备调试/投运流程；以后确实有批量换型需求，再增加“受控的运行时轴参数配置”。

换句话说：你现在因为首次调试偶尔需要重新编译一次 PLC，虽然不够灵活，但从全生命周期成本看，仍然比把脉冲换算搬到 servoV6 更便宜、更安全。

# 一、当前 AutoShop 的做法本身就是成熟做法

从截图看，AutoShop 的轴配置已经建立了完整的单位换算：

```
编码器脉冲数/电机转
        × 电机转数/工作台转数
        ÷ 工作台每转移动量
        = 脉冲数/工程单位
```

抽象后：

```
P = 编码器每电机转计数
R = 电机转数 / 负载转数
L = 负载每转移动量，单位 mm/rev

每毫米计数：
S = P × R ÷ L

位置：
counts = position_mm × S

速度：
counts_per_second = velocity_mm_per_second × S

加速度：
counts_per_second² = acceleration_mm_per_second² × S
```

这与其他成熟平台一致：

- Siemens 把齿轮比、丝杆螺距配置在轴 Technology Object 中，并以 mm 等工程单位解释运动命令。[Siemens S7-1500/T Axis Functions](https://support.industry.siemens.com/dl/files/348/109974348/att_1307007/v1/s71500_s71500t_axis_function_manual_en-US_en-US.pdf)
- Beckhoff 将编码器缩放定义为 mm/INC 或 °/INC，缩放配置属于 NC 轴，而不是上位应用。[Beckhoff TwinCAT NC scaling](https://infosys.beckhoff.com/content/1033/el7411/9983672587.html)
- CODESYS SoftMotion 也要求配置 increments 与 application units 的关系，IEC 程序使用工程单位。[CODESYS SoftMotion Light configuration](https://content.helpme-codesys.com/en/CODESYS SoftMotion Light/_sm_light_config_and_startup.html)
- Siemens SIMOTION 明确规定运动命令参数按轴技术对象中定义的工程单位解释，并在内部转换为增量。[Siemens Axis fundamentals](https://support.industry.siemens.com/cs/attachments/61055938/Axis_TechnologyFct_en-US.pdf)

所以 AutoShop 现在的“工作台旋转一圈移动量”不是多余配置，它就是运动轴坐标系的基础。

# 二、为什么不建议让 servoV6 计算脉冲

## 1. 它不只是换算一次速度

一旦上位机以脉冲为单位控制 PLC，所有运动相关数据都必须统一迁移：

- 绝对位置；
- 相对位置；
- 定位距离；
- 点动速度；
- 定位速度；
- 加速度；
- 减速度；
- 软限位；
- 原点偏移；
- 相对零点；
- 联动超差阈值；
- 同步轴齿轮比；
- 当前速度和当前位置反馈；
- 到位误差；
- 跟随误差；
- 日志、趋势图和报警显示。

servoV6 不能只把 `10 mm/s` 换成脉冲速度，却继续把 PLC 返回值当成 mm。最终必须形成双向转换：

```
servoV6 工程单位
    ↓
工程单位 → counts
    ↓
PLC 原始计数
    ↓
counts → 工程单位
    ↓
servoV6 状态与界面
```

这会让上位机承担原本由运动控制器承担的坐标系统责任。

------

## 2. 容易产生双重换算

当前 AutoShop 轴对象已经配置了工程单位换算。如果 servoV6 再把 mm 转成脉冲，然后把这个数传给 `MC_MoveAbsolute`、`MC_MoveRelative` 或 `MC_Jog`，PLC 会把这个“脉冲数”继续按工程单位进行一次换算。

例如：

```
期望速度：10 mm/s
servoV6 转换后：20000 counts/s
PLC 把 20000 当作 20000 mm/s
再通过轴配置转换一次
```

因此，除非完全绕过现有轴对象、改成底层脉冲输出控制，否则上位机不能直接向 PLCopen 运动功能块发送脉冲量。

而完全绕过现有轴对象意味着需要重新实现：

- 轨迹规划；
- 加减速；
- 位置控制；
- 限位；
- 回零；
- 停止；
- 同步；
- 错误处理。

这不是当前项目应该承担的成本。

------

## 3. 上位机不是实时运动控制器

servoV6 运行在 Qt/Android/Windows 环境，通过 Modbus TCP 通信：

- 调度周期不是确定性实时；
- TCP 有延迟、抖动、重传和断线；
- Android 可能进入后台；
- UI 线程可能卡顿；
- 上位机可能异常退出。

因此 servoV6 可以发送“目标位置 100 mm、速度 10 mm/s”，但不适合持续计算和发送脉冲轨迹。

CODESYS 允许控制器直接输出位置/速度设定值，但那属于实时控制器内部的运动控制场景，并且官方明确提醒必须完成缩放和安全验证。[CODESYS position control example](https://content.helpme-codesys.com/en/CODESYS SoftMotion/_sm_example_poscontrol.html)

------

# 三、方案 2 也分为两种，不能混淆

你说的方案 2 是：

> 上位机把 10 mm/s 发给 PLC，PLC 内部转换成电机实际速度。

这个方向正确，但有两种实现方式。

## 方案 2A：使用 AutoShop 运动轴原生换算

```
servoV6：10 mm/s
    ↓
PLC：MC_Jog / MC_MoveAbsolute 的 Velocity = 10
    ↓
AutoShop 轴对象根据配置自动换算
    ↓
驱动器/电机
```

这是最推荐的方案。

你当前 PLC 的 `轴控.FB` 已经按照这种方式调用：

- `MC_Jog`
- `MC_MoveAbsolute`
- `MC_MoveRelative`
- `MC_Home`

也就是说，当前 PLC 实际上已经采用方案 2A。

## 方案 2B：在 PLC 的 ST 程序中自己计算脉冲

```
servoV6：10 mm/s
    ↓
PLC ST：10 × 齿轮比 × 编码器分辨率 ÷ 丝杆螺距
    ↓
底层脉冲命令
```

不建议这样做，除非汇川当前运动轴对象完全无法满足要求。

因为这相当于抛弃 AutoShop 已有的：

- 坐标换算；
- 速度换算；
- 加减速度换算；
- 轴限制；
- PLCopen 状态机；
- 驱动器适配。

如果保留运动轴对象又增加 ST 换算，反而容易产生双重缩放。

# 四、齿轮比有误差时，正确处理的是什么参数

需要区分两类误差。

## 1. 理论参数录入错误

例如：

- 丝杆螺距填错；
- 齿轮齿数填错；
- 减速机比例填错；
- 编码器分辨率填错；
- 工作台每转移动量填错。

这种情况应该修正机械参数。

## 2. 实际标定误差

例如理论上移动 1000 mm，实测只有 998.7 mm。这可能来自：

- 滚轮有效直径与理论直径不同；
- 皮带轮有效节圆差异；
- 丝杆实际导程误差；
- 机械弹性；
- 打滑；
- 测量误差；
- 反向间隙。

标定时可以计算修正系数：

```
旧工作台每转移动量 = Lold
命令距离             = Xcmd
实际测量距离         = Xmeasured

新工作台每转移动量：
Lnew = Lold × Xmeasured ÷ Xcmd
```

例如：

```
Lold = 138.23 mm/rev
Xcmd = 1000 mm
Xmeasured = 998.7 mm

Lnew = 138.23 × 998.7 / 1000
     ≈ 138.0503 mm/rev
```

然后把 `138.0503` 填回 AutoShop 的“工作台旋转一圈的移动量”。

但如果误差来自反向间隙、打滑或非线性误差，仅修改比例并不能解决，需要另外做：

- 反向间隙补偿；
- 多点标定表；
- 外部编码器闭环；
- 机械维修。

------

# 五、不要同时开放所有机械参数

你提出希望开放：

- 齿轮比；
- 齿轮外径；
- 丝杆螺距。

这里有一个重要风险：这些参数可能互相重复。

例如，系统不应同时让用户自由输入：

```
齿轮比 = 30:1
主动齿轮齿数 = 1
从动齿轮齿数 = 30
```

因为两者表达的是同一个信息，可能出现配置冲突：

```
齿轮比写 30:1
齿数却写 20:1
```

建议按照机械拓扑选择参数。

## 丝杆模式

```
编码器计数/电机转
电机转数/丝杆转数
丝杆导程 mm/rev
方向
```

## 齿轮齿条模式

```
编码器计数/电机转
主动/从动齿轮齿数或减速机比例
齿轮有效节圆直径
方向
```

## 滚轮/皮带模式

```
编码器计数/电机转
减速机比例
滚轮或带轮有效周长
方向
```

## 旋转轴模式

```
编码器计数/电机转
电机转数/负载转数
负载一圈 = 360°
方向
```

内部最终都归一为一个权威值：

```
counts_per_engineering_unit
```

但界面保存的应是机械原始参数和标定记录，而不是让用户同时维护多个互相可推导的值。

另外，标准啮合齿轮通常使用齿数比，不使用外径比；“外径”更适合滚轮、摩擦轮、卷筒或皮带轮场景。齿轮外径可能包含齿顶，不能直接当作有效节圆直径。

# 六、运行时修改轴缩放的危险

如果把齿轮比、丝杆螺距开放给上位机动态修改，修改缩放后会影响：

- 当前绝对位置的解释；
- 已保存的相对零点；
- 软限位；
- 回零偏移；
- 未执行的目标位置；
- 联动超差阈值；
- 主从轴位置关系；
- 速度和加速度限制；
- 历史数据。

例如原来：

```
当前位置原始计数 = 2,000,000
比例 = 20,000 counts/mm
当前位置 = 100 mm
```

修改比例后：

```
比例 = 19,500 counts/mm
同一个原始位置突然变成 102.564 mm
```

机械没有动，但 PLC 显示位置发生跳变。

因此成熟系统即使支持运行时修改轴缩放，也通常要求：

1. 设备进入调试/维护模式；
2. 所有轴停止；
3. 电机去使能；
4. 解除电子齿轮或同步关系；
5. 清除所有运动命令；
6. 写入新参数；
7. 重新初始化轴对象；
8. 重新回原点；
9. 重新验证软限位；
10. 执行已知距离标定；
11. 保存配置版本和审计记录。

CODESYS 官方也明确指出，运行时修改缩放系数后需要重新初始化驱动轴。[CODESYS runtime reinitialization](https://content.helpme-codesys.com/en/CODESYS SoftMotion/_sm_special_use_cases.html)

目前还没有从公开的汇川资料中确认 H5U/AutoShop 是否支持安全地在运行时修改截图中的轴缩放配置。因此，在确认汇川提供正式的运行时配置接口前，不建议从 servoV6 直接写轴内部缩放参数。

# 七、三种实际方案的成本比较

## 方案 A：保留 AutoShop 配置

内容：

- servoV6 始终使用 mm、mm/s；
- 齿轮比、丝杆螺距在 AutoShop 中配置；
- 首次装机标定时编译下载 PLC；
- 量产后不再频繁修改。

估算：

| 项目         | 成本       |
| ------------ | ---------- |
| 开发         | 1–3 人日   |
| 单台首次标定 | 0.5–2 小时 |
| 系统验证     | 最低       |
| 长期维护     | 最低       |

非常适合：

- 机械结构基本固定；
- 参数只在首次投运时调整；
- 设备数量不大；
- 不频繁换型。

这正符合你描述的现状，因此当前最推荐。

------

## 方案 B：servoV6 计算并发送脉冲

估算：

| 项目                       | 成本       |
| -------------------------- | ---------- |
| 协议和领域模型修改         | 8–15 人日  |
| 位置/速度/加速度全链路换算 | 8–12 人日  |
| 联动、限位、回零改造       | 8–15 人日  |
| 测试与现场验证             | 10–20 人日 |
| 合计                       | 34–62 人日 |

同时会长期增加：

- 双向换算维护；
- 精度和溢出风险；
- 上位机与 PLC 配置不一致风险；
- 网络故障影响；
- 所有运动功能的回归测试量。

这是成本最高、风险最大的方案。

------

## 方案 C：servoV6 配置机械参数，PLC 轴对象完成换算

如果汇川提供正式、可靠的运行时轴参数设置和重新初始化接口：

| 项目                       | 成本       |
| -------------------------- | ---------- |
| PLC 参数结构及校验         | 4–7 人日   |
| 上位机配置界面             | 4–7 人日   |
| PLC 写入、回读、版本管理   | 4–6 人日   |
| 轴重初始化、回零和安全流程 | 5–10 人日  |
| 测试与现场验证             | 8–15 人日  |
| 合计                       | 25–45 人日 |

如果汇川不支持运行时修改，而需要自己绕过轴配置实现换算，成本会接近甚至超过方案 B。

# 八、最推荐的折中方案

建议分两期。

## 第一期：保留 AutoShop 为缩放权威

servoV6 增加“轴机械参数计算器”，但暂时不自动写入 PLC：

1. 用户选择机械类型；
2. 输入编码器分辨率、齿轮齿数、丝杆导程等；
3. servoV6 计算“工作台旋转一圈移动量”；
4. 用户输入标定命令距离和实测距离；
5. servoV6 计算修正值；
6. 生成一份 AutoShop 配置清单；
7. 工程人员将参数填入 AutoShop、编译、下载；
8. servoV6 保存配置版本和标定记录。

这样可以明显降低人工计算错误，但不改变运动控制架构。

预计只需 3–6 人日。

## 第二期：验证汇川运行时配置能力

单独做一个技术验证，不直接并入正式程序：

- 轴停止、去使能；
- 修改缩放参数；
- 重新初始化轴；
- 读取当前位置；
- 回零；
- 执行 100 mm、500 mm、1000 mm 标定；
- 测试掉电保持；
- 测试联动轴；
- 测试修改失败的恢复。

只有汇川官方接口和实机测试都证明可行，才把运行时配置加入 servoV6。

------

# 最终选择

按照你当前“只在第一次装机调试时发生”的实际情况：

> 继续采用 AutoShop 原生轴单位换算，servoV6 全程使用工程单位，是当前时间成本最低、工业风险最小的方案。

同时给 servoV6 增加一个“调试标定助手”，自动计算推荐的“工作台旋转一圈移动量”和修正系数，但暂时不直接改 PLC 轴内部缩放。

未来若设备批量化、机械频繁换型或现场无法使用 AutoShop，再投入方案 C：上位机管理机械配置，PLC 的运动轴对象负责最终换算和重新初始化。

不要选择方案 1，让 servoV6 直接把 mm 换成脉冲控制现有 PLCopen 轴。
