# NEMU 如何执行一条 RISC-V 指令

已知

```C
static const uint32_t img [] = {
  0x00000297,  // auipc t0,0
  0x00028823,  // sb  zero,16(t0)
  0x0102c503,  // lbu a0,16(t0)
  0x00100073,  // ebreak (used as nemu_trap)
  0xdeadbeef,  // some data
};
```

是 riscv32 设备初始存放到内存中的指令。并且 PC 指向内存的第一条指令：

```C
0x00000297,  // auipc t0,0
```

我们看下 NEMU 执行这条`auipc t0,0`指令的过程，这里使用 gdb 进行调试：

- 执行到

  ```c
  isa_exec_once(s);
  ```

  的时候，打印此时`s->pc`以及`s->snpc`均为`0x80000000`；

- 进入`isa_exec_once()`后，遇到了充满了宏定义的`decode_exec()`函数，不方便调试。

>
> ## 一、总体评价
>
> 你的笔记**事实层面基本准确**（`s->pc/s->snpc == 0x80000000`、AUIPC 模式匹配、`gpr[rd] = pc + imm` 这些观察都对），用 `gcc -E` 展开宏来理解 `decode_exec` 的思路也完全正确。
>
> 但作为对"第一条指令在 NEMU 中的执行过程"这个问题的**回答**，它**不完整且缺少闭环**：你的笔记几乎只描述了 `decode_exec` 这一层，而"执行一条指令"的关键结构——取指在什么时候发生、`snpc`/`dnpc`/`cpu.pc` 三者如何流转、CPU 下一条 PC 到底是谁、在哪一行代码写进去的——都没有讲清楚。答这种题，考官大概率期待的是从"启动装载 + 执行引擎循环 + 单条指令的取指-译码-执行-更新PC"的完整链条。
>
> ## 二、我实际验证的结果
>
> 在你的环境下跑了一次：
>
> ```
> (nemu) si
> 0x80000000: 00 00 02 97 auipc	t0, 0
> (nemu) info r
> t0  0x80000000
> pc  0x80000004
> ```
>
> 即：执行完第一条指令后 `t0 = 0x80000000`（`pc + 0`），`pc` 前进到 `0x80000004`。你的笔记结论与事实一致。
>
> ## 三、你笔记里各点的核对与问题
>
> **1. "`auipc t0, 0` 是内存第一条指令、PC 指向它" —— 基本正确，但缺了"谁把它放进内存"**
> - 内置镜像在 `src/isa/riscv32/init.c` 的 `init_isa()` 里被 `memcpy(guest_to_host(RESET_VECTOR), img, sizeof(img))` 拷到物理内存（`init_isa()` 在 `init_monitor()` 里先于 `load_img()` 调用，没给镜像文件时就用这个内建镜像）。
> - `restart()` 设置 `cpu.pc = RESET_VECTOR`。你的配置里 `CONFIG_MBASE = 0x80000000`、`CONFIG_PC_RESET_OFFSET = 0x0`（`include/memory/paddr.h:23`），所以 `RESET_VECTOR = 0x80000000`。
> - 如果你在笔记里补一句"`guest_to_host` 把客户地址映射到宿主数组 `pmem` 的偏移"，读者才能理解"客户内存"到底是什么。
>
> **2. "在 `exec_once()` 入口，`s->pc`、`s->snpc` 均为 0x80000000" —— 观察正确，但要说明这只是一个"初始赋值"**
> `exec_once()`（`src/cpu/cpu-exec.c:61-64`）开头就是：
> ```c
> s->pc = pc;    // 0x80000000
> s->snpc = pc;  // 0x80000000
> isa_exec_once(s);
> ```
> 所以你在进入 `isa_exec_once` 之前打印，两者当然相等。**但真正的顺序下一条地址不是在这里确定的**，见下一点——这是你笔记最大的盲区。
>
> **3. 你完全没提"取指"这一步，而这恰恰是 `snpc` 变成 `0x80000004` 的地方**
> `isa_exec_once`（`src/isa/riscv32/inst.c:75-78`）：
> ```c
> s->isa.inst = inst_fetch(&s->snpc, 4);  // 从 0x80000000 读 4 字节 → 0x00000297；同时 snpc += 4
> return decode_exec(s);
> ```
> `inst_fetch` 通过 `vaddr_ifetch → paddr_read → host_read`（宿主小端读出 `0x00000297`）取指，并且**在译码之前就把 `snpc` 推进到 `0x80000004`**。
>
> 所以正确的因果链是：
> > 你在 gdb 里看到的 `snpc == 0x80000000` 只是 `exec_once` 里的初始化值；等真正进入 `decode_exec` 时，`snpc` 已经是 `0x80000004`，随后 `decode_exec` 第一行 `s->dnpc = s->snpc;` 把顺序下一条地址记成 `0x80000004`。
>
> 如果你的笔记不澄清这一点，读者会以为"`decode_exec` 执行时 `snpc` 还是 `0x80000000`"，那就理解错了。
>
> **4. 对 `pattern_decode` 的描述用词不准**
> "`pattern_decode()`：格式化 AUIPC 指令格式" 表述含糊。它实际做的是：**把"位模式字符串"转成 `(key, mask, shift)` 三元组**，供后续比较 `((inst >> shift) & mask) == key` 使用（`include/cpu/decode.h:30-60`）。也就是说它在做"模式匹配"，不是"格式化指令"。对 AUIPC 而言，其低 7 位 opcode 是 `0x17`，`0x00000297 & 0x7f == 0x17` 命中。这一条你后面其实说对了，只是开头那句容易误导。
>
> **5. "命中后 `decode_operand` 解析操作数 + 执行体计算" —— 基本对，但漏了两个关键机制**
> - AUIPC 是 U 型，`decode_operand(..., TYPE_U)` 只算 `imm = SEXT(BITS(i,31,12),20) << 12 = 0`，`rd = BITS(i,11,7) = 5`（即 `t0`），于是 `gpr[5] = 0x80000000 + 0`。
> - 命中后紧跟 `goto *(__instpat_end)`，**直接跳到解码表末尾**（`INSTPAT_END` 的标签处），跳过 lbu/sb/ebreak/inv 等其他模式——这正是"每条指令只匹配一种模式"的实现方式。你笔记的省略号里其实藏了这个 `goto`。
> - 在解码表末尾还有一句统一收尾 `R(0) = 0;`（`inst.c:70`），用来强制 `x0` 恒为 0。你贴的 `.i` 片段里明明能看到 `(cpu.gpr[check_reg_idx(0)]) = 0;`，但你没有解释它。这条指令写的是 `t0(x5)` 不受影响，但理解这段代码时应该知道：**任何想写 `x0` 的指令在这里都会被抹掉**。
>
> **6. 最重要的问题：`decode_exec` 从头到尾不碰 `cpu.pc`，你笔记的叙事让人误以为"执行体赋值完指令就结束了"**
> `decode_exec` 只负责填 `s->dnpc`。真正的 PC 更新在 `exec_once` 的末尾：
> ```c
> isa_exec_once(s);
> cpu.pc = s->dnpc;   // cpu-exec.c:65  → cpu.pc = 0x80000004
> ```
> 然后 `execute()` 循环（`cpu-exec.c:92-101`）以 `cpu.pc` 作为下一轮 `exec_once` 的入参。也就是说：
>
> > "下一条 PC = 0x80000004" 是通过 `decode_exec 默认 dnpc=snpc` → `exec_once 写回 cpu.pc` 两步完成的。
>
> 你的笔记里没有这个闭环，所以严格来说你没回答"第一条指令执行完，CPU 怎么知道去 0x80000004"。
>
> **7. 其它小点**
> - 触发链路也建议补一句：`sdb 的 si → cpu_exec(1) → execute → exec_once`（`src/monitor/sdb/sdb.c:111`、`cpu-exec.c:118`）。另外你 `q` 退出那条路不用讲。
> - 你的调试手法（`make -nB | grep inst.c` 拿真实编译命令、`-c` 换 `-E`）没问题，注意要在项目根目录执行、且把 `-o` 指到临时文件即可，可以顺带 `grep -n` 定位 `decode_exec` 再 `sed` 分段看，避免一次输出太大。
>
> ## 四、建议的完整回答（可直接用于作答）
>
> 按下面五段组织，就把笔记里的内容串成完整回答了：
>
> 1. **装载与复位**：`init_monitor` → `init_isa()`：把内建镜像 `memcpy` 到客户物理内存 `0x80000000`（`guest_to_host` 映射到宿主数组 `pmem`），`restart()` 令 `cpu.pc = RESET_VECTOR = 0x80000000`、`gpr[0] = 0`。
> 2. **触发执行**：SDB 收到 `si` → `cmd_si` → `cpu_exec(1)`，状态置 `NEMU_RUNNING`，进入 `execute` 循环。
> 3. **取指**：`exec_once(&s, cpu.pc)` 先令 `s->pc = s->snpc = 0x80000000`；`isa_exec_once` 调 `inst_fetch(&s->snpc, 4)`，从小端内存读出指令字 `0x00000297`，并把 `snpc` 推进到 `0x80000004`。
> 4. **译码 + 执行**：`decode_exec` 先 `s->dnpc = s->snpc`（默认顺序执行）；用 `INSTPAT` 模式表匹配——`pattern_decode` 把 `"??????? ????? ????? ??? ????? 00101 11"` 解析成 key/mask/shift，`(0x00000297 & 0x7f) == 0x17` 命中 AUIPC；`decode_operand(TYPE_U)` 得 `rd = t0(x5)`、`imm = 0`；执行体 `gpr[5] = s->pc + imm = 0x80000000`；`goto` 跳到表尾后统一执行 `gpr[0] = 0` 维护 `x0` 语义，返回。
> 5. **PC 推进与结果**：回到 `exec_once`，`cpu.pc = s->dnpc = 0x80000004`；打印 ITRACE（`0x80000000: 00 00 02 97 auipc t0, 0`）。最终状态：`t0 = 0x80000000`，下一条将执行 `0x80000004` 处的 `sb zero, 16(t0)`（在 `0x80000010` 写 0），之后 `lbu` 读回 0 使 `a0=0`，`ebreak` 时 `NEMUTRAP` 以 0 退出——这正好是内建镜像"自检访存正确性"的套路。
>
