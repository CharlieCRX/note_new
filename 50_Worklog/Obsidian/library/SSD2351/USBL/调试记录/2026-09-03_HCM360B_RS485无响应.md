这类问题排查，本质是从 **应用层命令** 一路追到 **串口驱动、RS485 电气波形、芯片协议响应**。所以需要的是“跨层定位能力”，不只是会写代码或会看示波器。

**软件工程师需要的能力**

1. Linux 设备节点与串口基础
   要知道 `/dev/ttyS2` 是什么，UART2 如何映射到 Linux 设备节点，如何用 `stty`、`cat`、`echo`、串口工具验证串口参数。
2. 串口参数配置
   要理解这些参数的含义：

```
9600 cs8 -cstopb -parenb -ixon -ixoff -crtscts raw -echo
```

分别对应：

```
9600 baud
8 data bits
1 stop bit
no parity
no software flow control
no hardware flow control
raw mode
no echo
```

1. 二进制协议组帧能力
   要能按手册理解：

```
帧头、长度、地址、命令、数据、校验和
```

比如 HCM360B 查询帧：

```
68 04 00 04 08
```

需要知道每个字节是什么意思，checksum 怎么算，为什么少一个字节或长度错了设备就不回。

1. 十六进制与字节流调试能力
   要能区分：

```
发送字符串 "68 04 00 04 08"
```

和真正发送 5 个字节：

```
0x68 0x04 0x00 0x04 0x08
```

这是串口调试里非常常见的坑。

1. Linux 串口编程能力
   要会用 `open/read/write/poll/termios/tcsetattr/tcflush/tcdrain`，并理解阻塞、非阻塞、超时、缓冲区、raw mode 的影响。
2. 最小复现程序能力
   要能写一个绕开业务系统的 demo，例如 `hcm360b -n 5`，先证明“硬件链路 + 协议解析”通，再接入 `tyUSBL`。这一步非常关键，能避免在大系统里迷路。
3. 分层定位能力
   要能拆成：

```
串口是否能打开？
串口参数是否正确？
数据是否真的写出去了？
芯片是否有响应？
返回帧是否被读到了？
checksum 是否正确？
解析是否正确？
业务状态是否更新？
上位机接口是否返回缓存？
```

每层只验证一个假设。

**硬件工程师需要的能力**

1. UART/RS485 电气基础
   要理解 UART 是单端逻辑，RS485 是差分传输。开发板 UART2 经过 RS485 收发器后，线上看到的是 A/B 差分信号，不是普通 TTL UART。
2. 波特率与位时间计算
   例如 `9600 baud`：

```
1 bit 时间 = 1 / 9600 ≈ 104.17 us
```

发送一个 UART 字节通常是：

```
1 start bit + 8 data bits + 1 stop bit = 10 bit
```

所以 1 字节大约：

```
10 * 104.17 us ≈ 1.0417 ms
```

如果发 5 字节，大概就是 5.2 ms 左右。抓波时可以用这个判断波形时长是否符合预期。

1. UART 帧格式识别
   比如发送 `0x86`，二进制是：

```
1000 0110
```

UART 默认 LSB first，所以线上数据位顺序是：

```
0, 1, 1, 0, 0, 0, 0, 1
```

再加 start/stop bit，硬件工程师可以从波形上判断软件到底有没有发出正确字节。

1. 示波器/逻辑分析仪能力
   要会设置：

```
触发方式
时间基准
电压档位
差分测量
单次捕获
串口协议解码
```

如果是 RS485，需要看 A、B 两路，也可以看 `A-B` 差分结果。

1. RS485 方向控制排查
   很多 RS485 是半双工，需要 DE/RE 控制发送/接收方向。要能判断：

```
发送时 DE 是否拉起？
发送结束后是否及时切回接收？
RE 是否被错误关闭？
是否一直占用总线？
```

这类问题会表现为“开发板能发，但收不到芯片回应”。

1. A/B 线序与终端匹配
   要会检查：

```
A/B 是否接反
GND 是否共地
终端电阻是否合适
总线是否空闲偏置
线缆是否过长或干扰过大
```

A/B 接反时，常见现象是波形有，但设备完全不响应。

1. 电源与电平兼容
   要确认 HCM360B 供电、电平、RS485 收发器电压域是否正确。芯片没供电稳定，软件再正确也没响应。

**双方都需要的联合能力**

最重要的是建立一个共同的排查坐标系：

```
软件说：我写出了 68 04 00 04 08
硬件说：我在线上抓到了对应 5 个 UART 字节
软件说：我切回接收并等待响应
硬件说：设备是否回了差分波形
软件说：我 read() 是否读到了返回帧
软件说：checksum 和解析是否通过
```

这个过程里，软件和硬件要能对上同一个事实：**某个时间点，某个串口，以某个波特率，发出了某几个字节，线上波形是否对应，设备是否响应。**

**这次 HCM360B 排查中最关键的基础能力**

可以总结成这几类：

```
1. 看懂 Linux 串口设备节点和 termios 配置
2. 能把手册协议翻译成真实字节流
3. 能区分 ASCII 十六进制字符串和真正的 hex bytes
4. 能用最小程序隔离业务系统
5. 能用示波器/逻辑分析仪验证 UART/RS485 波形
6. 能根据波特率计算 bit 时间，判断波形是否合理
7. 能理解 RS485 差分、方向控制、A/B 线序和终端匹配
8. 能把软件日志、串口数据、物理波形按时间线对齐
```

一句话就是：

```
软件工程师要能证明“程序确实按协议写出了正确字节并读了正确响应”；
硬件工程师要能证明“这些字节确实变成了正确的 RS485 差分波形，并且设备具备响应条件”。
```

这才是嵌入式串口问题排查的核心能力。
