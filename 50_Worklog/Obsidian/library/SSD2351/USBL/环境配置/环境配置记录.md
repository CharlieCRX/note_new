任务目标是：

> 在 `ssd2351`上调用`libsdsonar.so`（驱动库）和`libuwac_runtime.so`（算法库）实现usbl水面设备业务。

已经验证的是`libsdsonar.so`已经在 ssd2351 开发板正常使用了，那么也要确保`libuwac_runtime.so`能够在 ssd2351 上正常运行。

要想实现这个任务，需要知道的是：

- 主程序、`libuwac_runtime.so`、`libfftw3f.so.3` 都要放到 ssd2351 目标板。
- 将库放到系统目录中`/usr/lib`
- 目标板上缺一个动态库，程序就无法启动。
- `ldd` 可以快速查看运行时依赖是否都能解析。

下面讲述了如何让`libuwac_runtime.so`在 ssd2351 上运行第一个 demo 的流程：

## 1.[[readelf - 解析 ELF 格式文件]]

**核心概念**：ELF 是 Linux 下可执行文件和动态库的二进制格式，本质上记录了平台架构、依赖库、符号版本、入口信息等。

**作用**：拿到陌生 `.so` 后，先用 ELF 信息判断它能不能在目标系统上运行。

常用命令：

```bash
readelf -h libuwac_runtime.so
readelf -d libuwac_runtime.so
readelf -V libuwac_runtime.so
file libuwac_runtime.so
```

重点看：

```
Machine: AArch64
(NEEDED)  [libfftw3f.so.3]
(NEEDED)  [libstdc++.so.6]
(NEEDED)  [libm.so.6]
(NEEDED)  [libgcc_s.so.1]
(NEEDED)  [libc.so.6]
GLIBC_2.35
GLIBCXX_3.4.30
```

笔记要点：

- `readelf -h` 看架构，例如 `AArch64` 表示 64 位 ARM。
- `readelf -d` 看动态依赖，即运行时必须加载哪些 `.so`。
- `readelf -V` 看符号版本，例如 `GLIBCXX_3.4.30`。
- ELF 可以理解为二进制程序和运行环境之间的“契约书”。

## 2.ABI 与[[符号版本]]

ABI 是应用程序二进制接口。即使函数名一样，如果 ABI 或符号版本不匹配，程序也可能无法运行。

**核心概念**：ABI 是应用程序二进制接口。即使函数名一样，如果 ABI 或符号版本不匹配，程序也可能无法运行。

典型报错：

```
GLIBCXX_3.4.30 not found
GLIBC_2.35 not found
```

检查命令[[strings - 提取二进制文件中的所有可打印字符]]：

```bash
strings libstdc++.so.6 | grep GLIBCXX
strings libc.so.6 | grep GLIBC_
```

笔记要点：

- `GLIBC_2.35` 表示目标系统的 glibc 至少要支持该版本符号。
- `GLIBCXX_3.4.30` 表示 `libstdc++.so.6` 至少要支持该 C++ ABI 版本。
- C++ 动态库尤其容易遇到 `GLIBCXX_xxx not found`。
- 只看库名不够，必须看符号版本。

## 3. Sysroot 机制

**核心概念**：Sysroot 是交叉编译时模拟目标板根文件系统的目录。

可以理解为：

```
宿主机 /usr/lib     -> x86 库，不能用于 ARM
sysroot/usr/lib    -> ARM 目标库，交叉编译时应该使用它
```

常见路径：

```
/path/to/toolchain/aarch64-unknown-linux-gnu/sysroot
```

这里要查询 **`sysroot` 中的 `libstdc++.so.6`（C++库）和 `libc.so.6`（C库）**，看它们**是否包含** `libuwac_runtime.so` 所需的那些版本标签。

经过验证，发现交叉编译工具链提供的C库和C++库是与`libuwac_runtime.so`版本匹配的：

> - **目标库要求**：`GLIBCXX_3.4.30` 和 `GLIBC_2.35`
> - **sysroot 实际拥有**：
>   - `libstdc++` 支持到 `GLIBCXX_3.4.30`（甚至更高）
>   - `libc` 支持到 `GLIBC_2.37`（因为工具链名带 glibc-2.37）

笔记要点：

- 交叉编译时，编译器和链接器应该只使用 sysroot 里的头文件和库。
- Sysroot 代表目标板环境，不代表宿主机环境。
- 缺什么目标库，就应该补进 sysroot，而不是链接宿主机 `/usr/lib`。
- 编译时看到的库版本最好不要高于真实目标板运行时版本，否则生成的程序可能在目标板上报 `version not found`。

## 4.FFTW 交叉编译

**核心概念**：当 sysroot 缺少目标平台依赖库时，需要从源码交叉编译补齐。

上面已经验证了`libuwac_runtime.so `依赖的其他库均能在交叉编译工具链的`sysroot/`中找到，并且C和C++版本兼容。此时缺失的`libfftw3f.so.3`就需要我们手动编译出来了。

示例流程：

```
./configure \
  --host=aarch64-unknown-linux-gnu \
  --enable-single \
  --enable-shared \
  --enable-neon \
  CC=/path/to/aarch64-unknown-linux-gnu-12.4.0-gcc \
  CFLAGS="--sysroot=/path/to/sysroot -O3 -mcpu=cortex-a53" \
  --prefix=/usr
  

make
make install DESTDIR=/path/to/sysroot
```

笔记要点：

- `--enable-single` 生成 `float` 版本，即 `libfftw3f.so`。
- `--enable-shared` 生成动态库。
- `DESTDIR=/path/to/sysroot` 用来把成品安装进 sysroot。
- `-mcpu=cortex-a53` 让编译器针对 Cortex-A53 生成更合适的指令。
- `--enable-neon` 把 NEON 优化路径编译进 FFTW。
- 最终应能看到类似文件：

```bash
sysroot/usr/lib/libfftw3f.so
sysroot/usr/lib/libfftw3f.so.3
```

这里还需要注意，我们需要启用 ARM 平台的 SIMD 指令集 NEON `--enable-neon `，可以让一条指令同时处理多组数据，适合 FFT、DSP、图像、音频等计算。

## 5.测试运行

上述步骤做完后，将`libuwac_runtime.so`以及所需要的所有动态库，打包上传到 ssd2351 开发板的`usr/lib`目录中。

分别编写 FFTW 和 `libuwac_runtime.so` 的 demo 程序，然后使用 ssd2351 交叉编译工具进行编译，上传到 ssd2351 进行测试即可。
