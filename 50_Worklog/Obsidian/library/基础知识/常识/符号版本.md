- 当你在 `libuwac_runtime.so` 中看到 `GLIBCXX_3.4.30`，它并不是一个单纯的字符串，而是**嵌入在二进制文件中的“最低消费要求”**。
- 编译时，GCC 链接器会把该库调用的每个 C++ 标准库函数，都打上一个“版本图章”（例如 `std::__cxx11::basic_string` 要求 `GLIBCXX_3.4.21`，某些新特性要求 `3.4.30`）。

#### 运行时检查（`ld-linux-aarch64.so.1` 的工作）

当你在目标板上运行程序时，动态链接器（`ld-linux`）会做以下事情：

1. 加载 `libuwac_runtime.so`，读取其依赖列表（`NEEDED`）。

2. 找到 `libstdc++.so.6`，检查它导出了哪些版本标签。

3. 如果 `libuwac_runtime.so` 要求 `GLIBCXX_3.4.30`，但目标板上的 `libstdc++` **只支持到 `3.4.29`**，动态链接器会立即报错并终止进程：

   ```text
   ./fftw_test: /lib/libstdc++.so.6: version `GLIBCXX_3.4.30' not found
   ```

4. 只有目标板上的库版本 **≥** 要求版本，才会放行。

#### 为什么你的 `sysroot` 匹配了，目标板就一定没问题？

因为你使用的**交叉编译工具链（gcc-12.4.0）** 和**目标板上的系统库**是同源的。既然你的 `sysroot` 里放的是 `glibc-2.37` 和 `gcc-12.4` 配套的 C++ 库，那么只要目标板也刷了对应的文件系统，就不会有版本冲突。**这就是为什么我们在主机上查 `sysroot`，就能预判目标板的运行情况**。
